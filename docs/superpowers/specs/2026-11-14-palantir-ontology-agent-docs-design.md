# Palantir Ontology 与 Agent 文档研究及复刻需求基线设计

## 意图与背景

老板希望先系统梳理 Palantir Foundry 的 Ontology（本体）与 Agent 相关官方文档，再以研究结论为依据复刻一个本体管理系统。后续目标栈包括 Vue 或 React 前端、Python + FastAPI 后端、Docker、微服务、Redis，以及 PostgreSQL 或 MySQL 等基础设施；具体产品范围与架构在研究阶段结束后单独设计。

当前阶段的受众是后续实现该系统的开发者。资料需要帮助读者理解本体对象模型、治理和写入机制，以及 Agent 如何在权限边界内读取或改变本体数据。

## 当前阶段目标

1. 编目 Palantir 官方文档中与 Foundry Ontology、Ontology 治理和 Agent 使用本体相关的页面，并记录标题、URL、语言、类别、页面更新时间（若可获得）、抓取/核对时间及研读状态。
2. 为英文文档查找官方中文对应页面；建立英中链接配对和覆盖情况，标出缺译、疑似过期或页面状态不同的条目。
3. 按主题分批为全部“直接相关”文档产出逐篇研读卡片：保留英文标题与官方原文链接，提供官方中文页链接（若有）、有限英文摘录及中文译文、中文要点解读、术语对照、译者疑问/待验证事项，以及对复刻系统的产品需求启示。
4. 汇总一份“复刻需求基线”，整理本体模型、操作、权限、安全、Agent 工具接入、审计和可观测性等能力，供第二阶段单独设计 MVP 与实现计划。
5. 提供可重复运行的官方文档编目脚本，支持后续重新发现页面、更新元数据和对比研读状态。

## 非目标与反目标

- 当前阶段不实现本体管理 Web 应用；文章梳理结束后，再针对系统本身完成设计与实现计划。
- 不抓取需要登录、付费或非公开访问的资料，不绕过访问控制。
- 不把 Palantir 整站文档全文镜像到仓库，也不逐字重印或翻译整篇受版权保护的文章。英文原文通过官方链接访问；研读卡片只保留每篇来源的少量英文摘录，并配中文译文和原创解读。若官方中文版本存在，优先链接该页面。
- 不声称复刻 Palantir 内部实现；目标是依据公开资料构建功能相似、边界清晰的本体管理系统。
- 不把产品公告中的历史状态当作现状；带有 beta、coming soon、deprecated 或更名信息的页面必须标注来源日期和核对日期。

## 资料范围

纳入与 Foundry Ontology 或 Agent 直接相关的官方文档页面，包括：

- Ontology 核心模型：对象类型、属性、链接类型、接口、共享属性、值类型、对象视图及资源管理。
- 数据映射与运行：对象数据源、索引/物化、函数、对象集、SDK 和 Ontology API。
- Ontology 操作与治理：Action Types、规则、参数、提交条件、回滚、写入历史、对象/资源权限、数据安全和权限检查。
- Agent 产品与运行：Agent Builder、Agent SDK、Pro-code agents、Agent Stack/Manager、会话、上下文项、事件、状态、工具、部署与调试。
- Agent 与 Ontology 集成：Ontology MCP、Palantir MCP、AIP Logic/Chatbot 中与 Ontology 工具、权限边界、提案审查、安全或审计直接相关的内容。
- 官方中文文档作为英文页面的对应译文资源；英文文档为当前术语及功能状态的主要依据。

目录中的每个页面都标记为“直接相关”或“补充参考”。本体建模/管理、Action Types、Ontology 权限、安全、Agent Builder、Agent SDK、Agent Stack/Manager、Pro-code agents、Ontology MCP 和 Palantir MCP 主题下与这些能力有关的页面均判为“直接相关”；Functions、AIP Logic、Workshop、Automate 和 SDK/API 等跨主题文档，仅当页面讲解本体数据读写、Agent 工具/会话接入、权限边界、审批或审计时判为“直接相关”。普通数据工程、分析、通用应用开发以及仅提供背景的页面列为“补充参考”。全部“直接相关”页面必须逐篇制作研读卡片；补充参考页面只编目并写明关联理由。

## 交付结构与研读格式

建议文件结构：

- `scripts/crawl_palantir_docs.py`：读取官方文档站点地图和人工维护的官方入口页，结合文档侧边栏链接发现相关页面；只写出元数据目录，不保存完整文章正文。
- `data/palantir_docs_catalog.jsonl`：逐页元数据、英文/中文对应关系和状态字段。
- `docs/research/README.md`：研究入口、主题索引、更新时间和目录生成方式。
- `docs/research/articles/`：每篇重点页面一份研读卡片。
- `docs/research/replica-requirements.md`：从资料中归纳的复刻需求基线。

每篇研读卡片采用以下字段：

1. 主题与研读状态。
2. 英文原文标题、官方英文链接、核对日期。
3. 官方中文标题与链接（若有），并标明它是官方译文还是本项目的中文解读。
4. 少量英文关键摘录与对应中文译文；同一来源直接摘录总量不超过 25 个英文词。
5. 中文要点解读，不复制整段原文。
6. 关键术语表和本体/Agent 领域中的译法说明。
7. 译者疑问或待验证事项；每条尽可能关联原文小节或链接。
8. 对复刻系统的设计启示及待落到需求基线的问题。

## 方案比较与选择

### 方案 A：全量镜像并逐篇全文翻译

覆盖最直观，但会复制大量官方文档内容，版权风险高；站点更新后维护成本大，也容易把旧译文误当成现行功能说明。因此不采用。

### 方案 B：先全量编目，再按主题研读并链接官方原文（采用）

以官方 sitemap 和文档导航发现页面，目录只存元数据；先为全部页面标注“直接相关”或“补充参考”，再对全部直接相关页面逐篇制作研读卡片并分批交付。利用官方中文版本，并为缺少中文版本的页面制作带短摘录、译文和原创解读的研读卡片。覆盖面和可维护性较好，也能逐步沉淀第二阶段的需求基线。

### 方案 C：只写一篇综述，不建逐页目录

交付快，但难以核对来源和文档版本，也不能支持后续分批阅读与增量维护，不适合作为复刻系统的研究底稿。

## 发现与更新方式

- 仅使用 Palantir 官方文档域名和官方公布的 sitemap/站内导航。
- 站点 sitemap 当前返回上限为 5,000 条，且混有不同语言和大量 API 页面；不能只依赖 sitemap。编目脚本需要结合若干官方主题入口页的侧边栏链接进行补充发现，并在目录元数据中说明发现来源。
- 请求遵循 `robots.txt`，使用低并发、请求间隔、缓存和有限重试；页面抓取失败或结构变化时记录错误，不静默丢弃。
- 抓取页面仅为读取标题、规范链接、语言/更新时间、栏目和导航元数据；研读正文通过官方页面人工核对，不落盘整篇正文。
- 英文与中文页面通过语言路径、标题/slug 和页面导航交叉匹配；自动匹配不确定时标记“需人工核对”，不得静默认定为同一版本。
- 目录应区分“发现日期”和文档本身的更新时间，所有产品状态判断均以核对当日页面为准。

## 研读批次建议

1. **本体基础与管理**：Ontology 概览、核心概念、对象/链接类型、属性、接口、Ontology Manager/资源管理。
2. **动作、函数与权限**：Action Types、提交条件、函数、对象编辑、对象权限与资源权限、安全模型。
3. **Agent 构建与运行**：Agent Builder、Agent SDK、Agent Stack、Pro-code agents、会话/事件/工具/调试。
4. **Agent 对接本体与系统边界**：Ontology MCP、Palantir MCP、应用限制、外部 Agent 数据流、人工审批和审计。

每批结束后更新主题索引和复刻需求基线。第一阶段的研读完成条件是：目录中每个“直接相关”页面均有一份研读卡片并标记为已完成；补充参考页面保留在目录中但不要求逐篇研读。完成后再单独进入系统产品设计，不在本设计文档中预先锁定应用模块、数据库 schema 或微服务拆分。

## 限制与风险

- 文档侧边栏、URL、语言版本和产品命名可能变化；脚本应保留失败记录和发现来源，目录需定期复核。
- sitemap 的条目上限会造成漏页；主题入口和递归导航是必要的补充来源。
- 官方中文译文可能缺失或落后于英文；配对信息必须带有人工核验状态和核对日期。
- 某些功能可能只对特定 Foundry enrollment 开放；公开文档不足以确认可用性时，应标成“公开资料未确认”。
- 复刻系统与 Palantir 的数据模型或权限语义不可能完全一一对应；需求基线应区分“官方明示事实”和“我们的设计推论”。

## 留给后续系统设计的决定

文章研读完成后，再决定本体管理系统的 MVP 范围、对象与关系建模方式、动作事务模型、权限策略、审计模型、Agent/MCP 接口、前后端技术选型，以及 Docker 与微服务部署边界。用户已提出 Vue 或 React、FastAPI、Docker、微服务、Redis 和 PostgreSQL/MySQL 等方向；第二阶段应在此基础上比较并给出明确选型。
