# 本体管理系统与 Agent 工作台设计

## 意图

老板希望在本地得到一套可启动、可操作、可继续扩展的 Palantir Ontology 能力复刻。系统要体现本体结构建模、治理审批、面向对象数据操作，以及 Agent 在显式授权下使用本体工具的完整链路。当前仓库只有官方文档元数据抓取与研究卡片脚手架，没有应用代码；Docker Compose、Python、Node.js 已安装。

## 目标

- 用中文界面管理 Ontology、对象类型、属性、链接类型和对象记录。
- 以提案审批保护结构修改，并记录版本、操作者和审计事件。
- 用 Action 执行经过参数/属性校验的对象数据变更。
- 管理 Agent 定义和工具授权；创建会话、调用只读查询或已授权 Action，并检查事件与审计记录。
- 本地通过 Docker Compose 启动前端、业务 API、Agent 运行服务、PostgreSQL 和 Redis；配置集中在环境变量与 Compose 文件。
- 给出演示数据、健康检查、初始化/迁移流程和中文使用说明。

## 非目标

- 不复制 Palantir 专有实现、商标或逐像素界面。
- 首版不调用外部大模型，不要求供应商密钥；Agent 工具可在界面中手动触发，接口留出后续接模型的位置。
- 不建设可横向扩展的企业级多租户 IAM、复杂策略语言或分布式工作流平台。
- 研究目录中的 676 张模板不作为系统交付完成的判据；已有官方来源可为领域规则提供依据。

## 架构方案

### 方案 A：模块化单体

一个 FastAPI 应用实现管理、对象、治理和 Agent，部署简单、跨域事务容易；但 Agent 会话和工具执行与管理 API 耦合，也无法满足用户提出的微服务方向。

### 方案 B：前端 + 本体 API + Agent 运行服务（采用）

Vue 3 单页应用经 HTTP 调用两个 FastAPI 服务。本体 API 是本体结构、对象、Action、身份与审计的唯一写入入口；Agent 运行服务管理 Agent、工具授权、会话和事件，通过内部 HTTP API 调用本体 API，所有工具调用传递操作者身份和能力范围。PostgreSQL 保存权威数据与持久审计；Redis 保存短期会话状态和事件队列。Docker Compose 编排全部服务。

以当前空仓库而言，这种拆分保留了清晰边界而不过度拆成许多空服务。Agent 服务即为独立微服务，后续可独立扩容。两服务共用本地 PostgreSQL 实例，但各自通过本体 API 访问受管业务数据。

### 方案 C：多服务与消息总线

额外拆出身份、动作、审计、工作流服务并引入 Kafka/RabbitMQ，可逼近大型平台形态，但会先增加部署和数据一致性成本，超出单人本地可交付 MVP 的需要。

## 技术选择

- 前端：Vue 3、TypeScript、Vite、Vue Router、Pinia；桌面优先的管理控制台。
- 本体服务：Python、FastAPI、SQLAlchemy 2、Pydantic、Alembic。
- Agent 服务：独立 FastAPI 应用；通过 Redis 维护活跃会话/事件，通过本体 API 调用授权工具。
- 持久化：PostgreSQL + JSONB；缓存/短期会话与事件：Redis。
- 首版不增加向量库、图数据库或对象存储：目前不做语义检索/文件资产；类型属性由 JSONB 承载，关系边由带源/目标类型索引的关系表承载。
- 本地开发与交付：Docker Compose；环境配置由 `.env` 提供，提交 `.env.example`，不提交密钥。
- 测试：Python `unittest`/FastAPI TestClient 和 Vue 项目现有或随项目固定的测试工具；测试业务行为、权限边界和 API 契约。

## 核心模块与行为

### 本体建模

默认工作区包含一个 Ontology。对象类型定义 API 名称、显示名称、描述、主键规则和属性；属性记录类型、必填/唯一/可编辑约束。链接类型定义源类型、目标类型及方向。结构新增与修改先形成提案，提交后等待具有管理权限的人审阅；批准时在事务中检查预期版本、应用变更、递增版本并写审计。拒绝保留原因和历史。首版提供新增对象类型、对象类型属性和链接类型提案。

### 对象与 Action

对象实例按对象类型校验并以 JSONB 保存业务属性。提供类型过滤、关键词搜索、分页、详情和链接浏览。Action 定义允许修改的属性和参数规则；执行前验证对象、字段白名单、数据类型与必填项，在单个事务内更新对象并记录前后值、操作者、Action 和时间。

### Agent 与工具

Agent 配置系统提示/说明、启用状态和显式工具授权。首版内置 `search_objects`、`get_object`、`execute_action`；每个工具都校验 Agent 授权、当前操作者权限及 Action 权限。会话状态可暂存在 Redis，重要事件和工具执行结果写入 PostgreSQL。界面支持创建/结束会话、手动调用工具以及查看逐步事件/结果。没有授权的工具不可见也不可执行。

### 身份、权限与审计

本地演示使用 JWT 登录和 `admin`、`editor`、`viewer` 角色：管理员能审阅/合并结构提案并管理 Agent；编辑者能创建提案和执行业务 Action；查看者只能读取。Agent 工具再以配置授权收窄能力。服务端是权限判定最终入口。审计覆盖 schema proposal 生命周期、Action、Agent 工具调用和授权失败；密码、令牌和完整敏感配置不进入审计正文。

## 完成标准

- `docker compose up --build` 可启动所有依赖，健康检查成功；全新数据库自动迁移并装入演示数据。
- 登录后可完成建模提案、审阅/批准、对象查询与编辑 Action、Agent 会话工具调用、审计查看的端到端流程。
- API 和 Agent 工具对未授权操作返回明确拒绝；并发的过期 schema 提案不能覆盖新版本。
- 测试覆盖上述关键规则，前端构建成功；中文 README 说明启动、账号、页面和 API。
- 无外部模型凭证时核心演示流程仍可完成；Git 不包含实际 `.env` 密钥。

## 实现者决定

用户授权自主选型并要求当前会话原生执行。选择两个后端服务而不是散拆更多服务；Redis 用于有实际读写的短期会话/事件；先实现可审计的确定性工具调用，不伪称接入了 LLM。官方资料中的 Agent Stack 会话状态、工具权限边界、Ontology 提案审阅、Action 事务等概念作为行为参考，产品细节由本项目自行实现。复核过的 GitHub 目标是 `danerlt/ontology-research`，按用户要求最终推送 `main`；SSH remote 与已配置的 SSH key 配套。
