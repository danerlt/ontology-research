## 英文原文短摘录（每个来源不超过 25 词）

> “Who can apply an action type with a given set of parameters?”

## 摘录译文

权限模型需要回答：谁可以使用给定参数集来执行某个动作类型？

## 中文要点

- Action 权限分为查看、编辑动作定义以及携带特定参数集执行三个面向。执行者必须能查看被编辑的对象/链接类型及其数据源，并通过独立配置的 submission criteria。
- 如果对象只允许经 Action 编辑，执行者对目标对象有 Read 权限即可提交，这意味着用户可能创建一个自己无法查看的新对象。若同时开放 Forms、直接编辑或 API 写回，数据集支持的对象通常要求执行者对写回数据集有 Edit 权限，该权限可能暴露该数据集更多数据；新对象类型默认仅允许 Action 编辑。
- 行/列访问策略在动作读取时过滤数据，但不会自动延伸到动作写出的数据；需通过 marking 或分类访问控制保证下游传播。动作创建日志对象或其他对象时，执行者也必须有这些对象类型所需权限，否则提交失败。
- 副作用有独立条件：配置 Webhook 插件需要额外权限；通知收件人需能访问消息中的对象数据，若通知发送失败，动作编辑仍可能成功。

## 术语对照

| 英文术语 | 中文译法 | 本页语境 |
|---|---|---|
| action type permissions | 动作类型权限 | 控制查看、编辑定义和提交动作的权限层。 |
| submission criteria | 提交标准 | 基于用户、参数与业务条件控制能否执行。 |
| writeback dataset | 写回数据集 | 对象编辑可落入的数据集，需要单独评估编辑权限。 |
| read-time enforcement | 读取时强制执行 | 行/列访问控制限制可读数据，不直接约束写出结果。 |

## 疑问与待验证项

- 中文对应页提示旧版权限正迁移到 Ontology 角色；英文页则重点说明动作权限与数据源权限组合，角色迁移状态需要结合当前环境说明核对。
- 页面指出数据读取边界不自动保护写出结果；具体 marking 传播策略需与读写授权和访问控制传播文档共同设计。

## 复刻启示

- 将“可浏览动作定义”“可修改动作定义”“可提交动作”“可读对象”“可写数据源”“可收通知”拆成权限对象；提交时同时校验并返回具体失败层。
- 默认通过动作服务修改对象，避免为编辑而授予过宽的数据集编辑权限；支持无法查看但可由受控动作创建的对象时，单独设计写而不读的 ACL。
- 对 Action log、下游敏感值和通知正文采用独立授权与最小披露，避免提交条件通过就被误解为拥有所有数据访问权。
